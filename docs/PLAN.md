# Project Plan — Sales Pipeline Intelligence for a European IT Consultancy
**dbt + DuckDB (data prep & business rules) → Python ML (win probability) → Power BI (executive dashboards) → AI (grounded vs. ungrounded test)**

> Status: v1.0 (locked with stakeholder, 24 Sep 2026) · Owner: *you* · Reviewer: Claude (brainstorm partner)
> All data is synthetic and generated by `scripts/generate_raw_data.py`. Company: **Nexora Consulting** (fictional).

---

## 1. The business problem (why this project exists)

Nexora Consulting sells IT services (Cloud, Data & AI, Cybersecurity, ERP) to companies across Europe.
The CRM is messy: a system migration in July 2025 changed field names and formats, reps type stages and
countries in different ways, accounts are duplicated, and amounts come in eight currencies.

The **Chief Revenue Officer (CRO)** asks four questions every Monday:

| # | Executive question | Dashboard page |
|---|---|---|
| 1 | Will we hit next quarter's number, and how healthy is the pipeline? | **Pipeline Health & Forecast** |
| 2 | Where are deals getting stuck, and how much money is at risk? | **Deal Velocity & Stuck Deals** |
| 3 | Which managers, teams and departments convert pipeline into revenue? | **Manager & Department Performance** |
| 4 | Where in Europe (country, industry, service) should we invest next? | **Europe Market Opportunity** |
| + | Can I trust these numbers? | **Data Trust** (small page) |

**The AI gap this project demonstrates:** an AI assistant pointed at the raw CRM export will answer these
questions quickly and confidently, but wrongly — it double-counts duplicates, adds GBP to EUR, treats
"Proposal Sent" and "3 - Proposal" as different stages, and doesn't know that Nexora forecasts with
*governed* stage probabilities rather than what reps type in. This project writes those business rules down
once (dbt models + `business_definitions.md`), proves the numbers reconcile to the CRM, and then shows the
difference it makes when an AI is grounded in them.

## 2. Scope

**In scope:** 24 months of CRM data (deals created Oct 2024 – Sep 2026, plus the CRM go-live import of deals
created Apr–Sep 2024), snapshot date **15 Sep 2026**. 18 European countries, 7 sales regions, 4 departments,
8 sales managers, 29 account executives, ~720 client accounts, ~4,800 opportunities.

**Out of scope:** marketing leads before they become opportunities, invoicing/revenue recognition,
live CRM connection (we work from exports, as most analysts do).

**Tools (all free, no licence expiry):** dbt Core + DuckDB (SQL transformation, tests, docs) · Python (scikit-learn) for the
model · Power BI Desktop · Git + GitHub + GitHub Actions · a free AI chat assistant. The first iteration of the data prep was
built in Alteryx; that work is kept in `archive/alteryx_v1/` and its row counts are the benchmark the dbt version reproduces.

## 5. dbt design

```
dbt_project.yml · profiles.yml           # dbt Core + DuckDB, no server needed
data/reference/*.csv                     # dbt SEEDS: governed business rules stored as data
macros/                                  # standardise_opportunity_columns (mapping-driven), parse_date/amount/probability, alias()
models/
├── staging/        stg_crm__*           # read raw files, type and parse, apply governed aliases (views)
├── intermediate/   int_*                # versions + test flags, master accounts, owner matching, stage events -> stints (views)
└── marts/          pipeline_deals ...   # business-ready tables that Power BI reads (tables)
tests/                                   # singular tests, incl. "any failed reconciliation check fails the build"
ml/win_probability.py                    # leakage-safe model: photos, backtest, train, score -> `ml` schema
scripts/                                 # generate_raw_data.py · run_pipeline.py · export_outputs.py
```

| Layer / model | What happens | Replaces (Alteryx v1) |
|---|---|---|
| `stg_crm__opportunities` | `read_csv(opps_*.csv, union_by_name)` reads all 24 files; the **`standardise_opportunity_columns` macro** builds one COALESCE per field from `crm_field_mapping_v1_v2` | Batch macro + Dynamic Rename |
| `stg_crm__accounts` | `read_xlsx(range 'A4:J5000')` skips the 3 junk rows, `ACC-%` filter drops the footer; country / industry / size via aliases; swapped lat/long fixed | Input (start on line 4), Find Replace, Formula |
| `stg_crm__sales_roster`, `stg_crm__stage_history` | Typed roster; audit log reduced to Stage rows with 3 timestamp formats parsed | Formula, Filter |
| `int_opportunity_versions` | Rank versions per deal (latest = 1), flag CRM test records | Sort, Unique |
| `int_accounts_master` | Normalised company key (case, spaces, dots, legal suffix) -> lowest account_id is master; coordinates filled from city average | Formula (REGEX), Summarize, Join |
| `int_opportunities_clean` | Latest real version; owner resolved in passes (exact name -> "Last, First" -> initial + surname -> alias); currency filled; accounts linked | Join (L/R outputs), Union |
| `int_stage_events` / `int_stage_stints` | De-duplicate events **after** parsing; `lead()` window closes each stint; exit type = Advanced / Regressed / Won / Lost / Open | Multi-Row Formula (grouped) |
| `pipeline_deals` | Governed probability, FX at close month (won/lost) or snapshot month (open), outliers, stuck / stale / past-due / at-risk, deal type, account status, DQ flags | Container E |
| `dq_reconciliation` | 27 checks against `crm_control_totals` + row bridges + integrity checks; `status <> 'PASS'` fails `dbt build` | Container F (Test tool) |
| `rejected_records` | Every raw row that did not become a deal, with the reason | Rejected-records output |

`ml/win_probability.py` follows the original five-step design: **H1** photos of closed deals at day 0/14/30/45/60/90/120 of each stage,
**H2** time-based split at 1 Mar 2026 (all photos of a deal stay on one side), **H3** Logistic Regression + Random Forest,
**H4** Brier score, AUC, calibration, business backtest, **H5** retrain on all history and score today's open deals. See `docs/model_card.md`.

**Design rules to show off in the README:**
1. Business rules stored as reference data (`stage_rules.csv`, `value_aliases.csv`), loaded as dbt seeds, not buried in SQL.
2. Every join is checked: unmatched rows are counted and either fixed or flagged (`dq_flags`), never dropped.
3. Nothing is silently deleted: removed rows go to `rejected_records` with a reason.
4. The build reconciles to CRM control totals and **fails** if it doesn't (dbt tests + `dq_reconciliation`).
5. One variable (`snapshot_date: 2026-09-15` in `dbt_project.yml`) drives every "as of" calculation.
6. Reproducible: seeded data generator + `python scripts/run_pipeline.py` rebuilds everything; CI runs it on every push.

## 6. Power BI design

**Canvas:** 16:9 page (1280 × 720), `powerbi/theme.json` applied. **Style:** dark navy title bar, white background,
one accent colour per meaning: Won = green, Lost = grey, open stages = sequential blues, risk = amber/red.
Every page has: title that states the question, 4–6 KPI tiles, 3–4 charts, filters on the right,
a one-line "So what" text box written by you.

**Data sources:** the CSVs in `data/output/powerbi/`, joined with **relationships** (full model in `powerbi/README.md`) — `pipeline_deals` ↔ `pipeline_stage_stints`
(opportunity_id), `pipeline_deals` ↔ `sales_team` (owner_email). `dept_quarter_summary` is a separate
source filtered with the shared `department` field.

### Page 1 — Pipeline Health & Forecast (main page)
- KPI tiles: Open Pipeline €, Weighted Pipeline €, Q3-2026 Bookings vs Target %, Next-Quarter (Q4-2026) Coverage ×, Win Rate (last 12 months), Average Won Deal €.
- Open pipeline funnel by stage (count and €) with stage-to-stage conversion %.
- Forecast by expected close quarter: stacked bar (Commit / Best Case / Pipeline, weighted €) with target reference line.
- Monthly bookings trend vs quarterly target.
- Filters: Department, Sales Region, Service Line.

### Page 2 — Deal Velocity & Stuck Deals
- KPI tiles: € At Risk, # Stuck Deals, Average Sales Cycle (won, days), # Past-Due Close Dates.
- Median days in stage vs stuck threshold (reference line), by stage; heatmap department × stage.
- Scatter: days in current stage vs deal €, coloured by risk reason.
- "Fix-this-week" table: top 15 at-risk deals (owner, stage, days stuck, last activity, €, reasons).
- Regressions (deals that moved backwards) by department.

### Page 3 — Manager & Department Performance
- Department → Manager → AE drill-down: FY2026 bookings, win rate, open pipeline, average cycle.
- Bullet chart: AE quota attainment year-to-date (prorated quota).
- Scatter per manager: open pipeline € (x) vs win rate (y), bubble = bookings.
- Forecast honesty: average gap between rep-entered probability and governed probability, by manager.
- Loss reasons by department (100% stacked bar).

### Page 4 — Europe Market Opportunity
- Map: countries filled by open pipeline €, dual-axis city bubbles (size = pipeline, colour = industry).
- Heatmap industry × sales region: colour = win rate, label = pipeline €.
- Pipeline by service line for the selected region (map acts as a filter).
- Top accounts table with account status (Active Customer / Prospect).

### Page 5 — Win Probability (ML)
- Calibration chart: predicted vs actual win rate by probability bin, model vs governed, with a 45° reference line.
- Backtest: governed forecast € vs model forecast € vs actual won € for the pipeline of 1 Mar 2026.
- "Gut vs rules vs data": average rep, governed and model probability by manager.
- Open-deal review list: deals where model and governed probability differ by ≥ 25 points.
- (Page 1 also gets an *advisory* Model-weighted Pipeline € tile.)

### Page 6 — Why this deal? (ML explainer)
- List of open deals (click one). Cards: model win probability, CRM stage default, average open deal, deal value.
- Plain-words reasoning for the selected deal, a bar chart of each driver's impact in points (up / down), and a table of the facts behind each driver.

### Page 7 — Data Trust (small)

(€ vs count toggle), drill-through, bookmarks and page navigation, conditional formatting, report-page tooltips, filled map.

## 7. AI experiment design (the differentiator)

Same five questions, asked twice to a free AI assistant, compared with the reconciled "ground truth" (Power BI / dbt marts):

| Round | What the AI gets | Expected outcome |
|---|---|---|
| A · Ungrounded | `raw_union_uncleaned.csv` | Fast, confident, and wrong in specific, explainable ways |
| B · Grounded | `pipeline_deals_for_ai.csv` + `business_definitions.md` | Matches the ground truth (or close) |

The ML model and the AI assistant play different roles: the **model** produces a number (win probability) from history; the **AI assistant** explains and summarises numbers. Both are only trustworthy on top of governed, reconciled data.
| C · Narrative | Round B context + "write the CRO's Monday summary" | You verify every claim against the dashboard and log it |

Full protocol in `ai_experiment/README.md`.

- **Data & AI** creates the most pipeline and is growing fastest, but deals sit ~50% longer in **Proposal** (GenAI budgets awaiting approval).

- **Public Sector** stalls in **Negotiation** (procurement) and in Solution Design.
- **Energy & Utilities** (energy transition) is a high-converting industry, concentrated in DACH and the Nordics.
- About a third of open pipeline breaches a stuck threshold — pipeline hygiene is itself an executive insight.
- A departed rep still owns open deals (orphaned pipeline).
- The governed stage probabilities are **too optimistic**: on the 1 Mar 2026 backtest they overstate won € much more than the ML model does, which is a reason to recalibrate `stage_rules.csv`.
